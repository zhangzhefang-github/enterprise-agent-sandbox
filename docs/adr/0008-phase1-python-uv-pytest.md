# 第一期实现基线：Python、uv 与 pytest

第一期的业务核心和自动化测试使用 Python（`>=3.12`），依赖由 uv 管理，测试用 pytest。金额继续使用 `decimal.Decimal`。这是第一期的实现基线，用来让后续切片共用同一套工具链；它不是永久不可变的技术承诺，以后可以用新的 ADR 替换。

选择 Python，是因为被测 Agent 的模型与工具生态以 Python 为主，评测运行和参考工具层可以放在同一进程里直接调用业务操作接口。uv 锁定依赖和 Python 版本，避免各切片各装一套环境。pytest 只通过公开接口断言业务结果，和“测试不依赖内部实现”的约定一致。金额用 `Decimal`，是为了让单价容差和应付金额不受二进制浮点误差影响。

## Considered Options

- TypeScript（vitest 或 node:test）：工具层生态同样常见，但模型脚本和十进制定点会分成两套运行时，第一期不采用。
- 不记录选型、让每个切片自行选择语言和测试框架：工具链会分叉，同一条评测无法重复运行，不采用。

## Consequences

- 新代码沿用这一基线，直到出现取代它的 ADR。更换语言或测试框架不改变 P2P 规则集，但会中断现有测试，应单独决策。
- 单价、容差和应付金额使用 `Decimal`，不用二进制浮点比较。
- 数量在第一期按不可分割的整数件实现（`int`）。H8 只约束单身份、单仓库、单币种、不含税，以及不涉及批次、序列号和质检，并不能推出数量必须是整数。整数件是实现假设：已冻结的验收场景全部以“件”给出，没有分数数量；`int` 乘 `Decimal` 单价仍得到精确金额。若以后的场景需要可分割数量，应把数量改为 `Decimal`，比较和不变量保持不变。在业务规则本身没有改变时，这一类型调整不视为规则集版本变更。
